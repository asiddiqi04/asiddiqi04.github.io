01

Introduction

This report covers my Summer 2026 co-op term at TextNow, my second term in a row on the same team. In the winter I proved I could ship a system end to end. This summer I was trusted to lead one. My primary assignment was Automated Onboarding, a program that replaces a paid third-party SaaS tool with software we own. It covers both IT identity provisioning and HR hire processing.

If the winter term was about learning to build, this term was about learning what it takes to make software trustworthy: idempotency, failure isolation, honest metrics, security boundaries, and documentation written for the people who inherit the system after you leave. That thread runs through everything below.

02

Goals and Learning Outcomes

Own a production system end to end

I wanted responsibility for a system's whole life: design, build, testing, security review, documentation, and go-live. Leading the onboarding program gave me exactly that, including credential audits, runbooks, and a manual review process before anything touched production.

Learn real reliability engineering

Classroom code rarely fails; production code fails constantly. I set out to learn how engineers design for failure and made real progress: root-causing an 18-alert incident down to 3 meaningful alerts, designing per-hire failure isolation, and proving idempotency with re-run tests instead of assuming it.

Lead, not just build

As project lead on two tracked programs, I wrote seven project health updates with honest percentages, negotiated integration details with IT and HR stakeholders, and turned a PM's project plan into a dependency-wired ticket graph. Leading meant communicating as much as coding.

Looking back, I grew most in reliability engineering and stakeholder communication, skills I could only have developed on a system real people depend on. Next I want to learn how these same principles hold up at much larger scale.

03

What I Built

Project 01 · Primary Assignment

Project lead

Automated Employee Onboarding

An orchestration platform that replaces a paid SaaS product with software TextNow owns. It takes a new hire from the moment HR signs them to a fully provisioned employee: HRIS record, service-desk ticket, Active Directory account, access groups, manager assignment, welcome communications, and an audit trail for every step.

What I built

  • The IT pipeline: detects new hires in Dayforce (the HR system), opens a service-desk ticket, and creates the employee's Active Directory account with collision-safe username and email generation that handles duplicate and non-ASCII names. It then looks up the access groups for the hire's department and provisions them idempotently, so re-running the pipeline never applies anything twice.
  • The P&C pipeline: takes signed offers from Greenhouse (the recruiting system) and creates the hire record in Dayforce. We designed this step with a dedup guard to ensure the same hire is never created twice. The pipeline then sets up the employee's file storage, sends the new-hire welcome emails and Slack messages, notifies the manager, and routes the signed offer documents.
  • Reliability engineering: root-caused a live incident where retry logic multiplied 6 expected alerts into 18, and drove alert noise per failing hire from 18 down to 3; designed per-hire failure isolation so one bad record never kills the batch; wired all 20 workflows to a shared error handler with stage-by-stage progress narration on each ticket.
  • Security engineering: sensitive personal data flows through an isolated path with execution logging disabled, and we verified by testing that nothing leaks. Access is granted on a least-privilege basis by employment type, every credential went through a production-readiness audit, and when an elevated API credential began exposing Social Security numbers we escalated it right away.
  • Documentation for handoff: an operational runbook, a maintenance guide organized by scenario, and a deep-dive for each subsystem, so the IT and HR teams can operate the system on their own.
n8n Dayforce REST Active Directory / LDAPS Jira Service Management Jira Assets Microsoft Graph Greenhouse Harvest Slack OpenSpec

Why it matters: onboarding a new employee used to depend on a paid external tool plus manual IT work, with no unified audit trail. The platform we built is owned in-house, narrates every step on a ticket a human can read, and fails safely: a diverted hire raises an alert instead of a half-provisioned account. A teammate summed up the ambition best: "once your onboarding flow is done, we can technically automate any IT ticket."

Project 02 · Platform Engineering

Creator & maintainer

Streamlit-on-Snowflake CI/CD Platform

Carried from the end of my winter term into early summer: I generalized my single dashboard project into TextNow's shared monorepo and deployment pipeline for Streamlit apps on Snowflake. Other teams can now deploy their own apps through it without help.

What I built

  • A monorepo contract (each app declares its own deploy config) with lint, syntax, and config validation on every push, and a step-by-step onboarding guide with copy-paste templates so teams can add an app without asking for help.
  • A two-workflow GitHub Actions design: a dispatcher that validates inputs and fails fast on missing config, and a reusable deploy workflow that injects environment-specific settings at deploy time and ships via the Snowflake CLI.
  • Release gating: separate staging and production environments, a required reviewer approval before anything deploys to production, environment-scoped secrets, and concurrency controls so deploys can't overlap.
GitHub Actions Snowflake CLI GitHub Environments Ruff Python

Why it matters: the real test of a platform is whether someone else can use it without you. Another engineer deployed a much larger analytics app through the pipeline without modifying it, and the repo has since become a maintained internal asset with additional security hardening added by the reliability team.

04

Conclusion

The single idea that ties this term together is that shipping is the beginning, not the end. Every system I touched this summer was judged by how it behaves when things go wrong: does a failed hire divert cleanly, does a re-run stay idempotent, can the next person operate it from the docs alone? Learning to ask and answer those questions is the difference between code that works in a demo and software an organization can rely on.

If someone were to summarize this report, I would want them to say: he was given real responsibility, treated reliability and honesty as engineering requirements rather than virtues, and left behind systems that other people can run without him.

Introduction

My goal for this website is to give a clear picture of what I worked on, what I learned, and how the term helped me grow as a software engineering student. I worked at TextNow during the Winter 2026 co-op term as a Full-Stack Software Developer Co-op, contributing to projects that supported internal teams and customer-focused product thinking.

02

About TextNow

TextNow is a communications company best known for helping people call and text through an app-based phone service. The company works in an area of computing that connects mobile apps, cloud services, data systems, internal platforms, and customer experience. During my term, I saw how software supports both the product users see and the internal systems employees rely on every day.

What stood out to me was the range of problems a software team can touch inside one company. Some work was close to the customer experience, while other work focused on making internal processes faster, clearer, and easier to manage.

03

Goals and Learning Outcomes

Build Useful Internal Tools

I wanted to improve at building software for real teams, not just for a class assignment. This goal was met through projects where I had to understand how employees worked, what information they needed, and how to make tools fit into existing processes.

Grow My Automation Skills

I wanted to learn how companies reduce repetitive work through automation. I made progress on this by working on feedback collection and onboarding workflows that moved information between systems with less manual effort.

Practice Clear Technical Communication

I wanted to get better at explaining technical work to people with different backgrounds. This goal became important when writing documentation, presenting product ideas, and turning project details into language stakeholders could understand.

Connect Software to Business Value

I wanted to understand how engineering decisions support business goals. The innovation challenge helped me see how customer feedback, product strategy, and implementation planning can come together in one proposal.

Looking back, I was most successful in improving my automation, communication, and product-thinking skills. I still want to keep growing in system design, especially around how larger services are maintained after the first version is built.

04

05

Conclusion

This work term showed me how software engineering creates value beyond writing code. The strongest projects started with a real need: a team needed clearer feedback, IT needed a more reliable onboarding process, and product stakeholders needed a better way to understand customer motivation. My role was to help turn those needs into systems, plans, and explanations that could be used by other people.

If someone were to summarize this report, I would want them to say that I learned how to connect technical work with human problems. I became more confident building practical tools, communicating with stakeholders, and thinking about software as part of a larger organization.
